# Duckov 모작

> **문서 상태**: Pre-production / M0 설계 진행 중
> 
> 
> **문서 목적**: 언리얼 콘텐츠 프로그래머(UI) 포트폴리오에서 무엇을 만들고, 어떤 기술 역량을 어떻게 검증할지 빠르게 설명한다.
> 

## 1. Executive Summary

| 항목 | 내용 |
| --- | --- |
| 프로젝트 | Duckov-Like (가칭) |
| 장르 | 싱글플레이 탑다운 익스트랙션 슈터 |
| 플랫폼 | PC (Windows) |
| 엔진 | Unreal Engine 5.7 |
| 핵심 산출물 | 테스트 가능한 Grid Inventory Model + UE MVVM 기반 UMG UI + 최소 레이드 루프 |
| 레퍼런스 | Escape From Duckov의 익스트랙션 루프와 그리드 인벤토리 상호작용을 분석 대상으로 사용 |
| 현재 단계 | 인벤토리 구조 설계를 확정하기 전의 M0 단계 |

### 한 문장 정의

**아이템 배치 규칙을 Model에 집중하고, UMG MVVM으로 표현한 그리드 인벤토리를 실제 루팅-탈출 루프에 연결하는 UI 프로그래밍 포트폴리오 프로젝트다.**

> **담을 내용**: Escape From Duckov의 인벤토리 화면 전체. 좌측 캐릭터/장비 슬롯 + 우측 그리드 소지품이 한 화면에 보이고, 크기가 서로 다른 아이템(1x1 탄약, 2x3 소총 등)이 섞여 배치된 상태.
**여기 넣는 이유**: “그리드 인벤토리”가 무엇인지 심사자가 3초 안에 이해하게 하는 기준 화면. 이후 모든 섹션이 이 화면의 부분을 설명한다.

## 2. 프로젝트 목표와 성공 기준

이 프로젝트의 목적은 완성도 높은 상용 게임 제작이 아니라, **인벤토리 시스템을 직접 설계하고 검증 가능한 형태로 구현하는 역량**을 보여주는 것이다.

| 성공 기준 | 증빙 방법 |
| --- | --- |
| 설계 의도를 설명할 수 있다 | 클래스/데이터 흐름 다이어그램, ADR |
| 설계와 구현의 책임 분리가 유지된다 | Model, ViewModel, View 의존 방향 검토 |
| 핵심 규칙이 재현 가능하게 검증된다 | Model Automation Test 결과 |
| 시스템이 게임 안에서 동작한다 | 루팅 -> 정리 -> 탈출 -> 스태시 이관 데모 |
| UI 성능을 근거로 설명할 수 있다 | 위젯 수, Tick, 갱신 범위 프로파일 |

## 3. 플레이 루프

`스태시에서 장비 세팅 -> 레이드 진입 -> 루팅/전투 -> 탈출 성공 시 스태시 반영`

- 탈출 성공: 레이드에서 획득한 아이템을 스태시에 커밋한다.
- 사망: 레이드 인벤토리를 폐기한다.
- 이 루프의 역할: 인벤토리가 독립 UI가 아니라 게임 상태와 연결된 시스템임을 증명한다.

## 4. 범위 관리

### P0: 반드시 구현

- 크기, 회전, 스택, 분할, 병합을 지원하는 그리드 인벤토리
- 아이템 Definition과 가변 Instance의 분리
- 플레이어 인벤토리, 루팅 컨테이너, 스태시의 공통 컨테이너 처리
- 드래그 앤 드롭, 회전, 퀵 이동, 자동 정렬, 툴팁
- 저장/로드
- 맵에서 아이템 획득 -> 인벤토리 조작 -> 탈출 -> 스태시 이관의 최소 루프

### P1: 인벤토리 사용 맥락을 위한 최소 게임플레이

- 탑다운 이동, 조준, 사격과 무기 1~2종
- 단순 AI 적 1종과 루팅 가능한 시체 컨테이너
- 레이드 맵 1개와 탈출 지점
- 무기/방어구/가방 장비 슬롯이 게임플레이 상태에 반영되는 흐름
- 사망 시 레이드 장비 손실

### P2: 여유가 있을 때만

- 상인, 무게-이동속도 연동, 납품형 퀘스트
- 중첩 컨테이너, 미확인 아이템
- 사운드와 이펙트 폴리시

### 의도적으로 제외

- 네트워크 및 Replication
- 베이스 건설, 펫/동료, 스킬 트리
- 다수의 맵, 적, 무기, 퀘스트 콘텐츠

> 범위 판단 기준: 인벤토리의 구조적 완성도나 검증 가능성을 높이지 않으면 v1에서 제외한다.

## 5. 핵심 시스템: Grid Inventory

### 기능 요구사항

| 영역 | 요구사항 |
| --- | --- |
| 아이템 데이터 | 크기, 스택 상한, 카테고리, 아이콘, 무게를 Definition으로 관리 |
| 아이템 상태 | Definition 참조, 수량, 회전, 위치, 내구도 등 가변 상태를 Instance로 관리 |
| 그리드 | 임의 크기의 2D 그리드, 경계/겹침/카테고리 규칙 검사 |
| 조작 | 드래그 앤 드롭, R키 회전, 스택 분할/병합, 퀵 이동, 자동 정렬 |
| 컨테이너 | 플레이어, 상자, 시체, 스태시에 동일한 이동 규칙 적용 |
| 장비 | 무기, 방어구, 가방은 그리드와 구분되는 슬롯 규칙 적용 |
| 영속성 | 스태시와 인벤토리 상태 저장/로드 |

> **담을 내용**: ①아이템을 집어 다른 칸으로 드래그해 놓기(셀 스냅) → ②드래그 중 R키로 90도 회전 → ③스택 아이템 분할/병합. 한 클립에 이어 붙이거나 3개로 분리.
**여기 넣는 이유**: 위 표의 “조작” 행 한 줄이 이 프로젝트 P0 작업량의 절반이다. 글로는 난이도가 전달되지 않고, 특히 **드래그 중 회전**이 D2(드래그 구현 경로) 결정을 좌우하는 요구사항임을 보여준다.

> **담을 내용**: 좌측 시체/상자 컨테이너 + 우측 플레이어 소지품이 동시에 열린 상태. 두 그리드의 셀 크기·상호작용 방식이 동일함이 보이게.
**여기 넣는 이유**: 위 표 “컨테이너” 행의 *동일한 이동 규칙 적용*이 왜 설계 원칙인지의 근거 화면. 레퍼런스에서도 루팅 UI가 별도 시스템이 아니라 같은 그리드의 재사용임을 시각적으로 보여준다.

### 아키텍처 원칙

1. **Single source of truth**: 위치, 회전, 수량은 Model만 소유한다.
2. **단방향 의존성**: `UMG View -> ViewModel -> Model`만 허용한다.
3. **원자성**: 컨테이너 간 이동은 전체 검증 뒤 한 번에 커밋한다. 실패 시 양쪽 상태는 변하지 않는다.
4. **명시적 실패**: UI가 `NoSpace`, `Occupied`, `InvalidCategory`, `StackFull` 등의 실패 이유를 표시할 수 있어야 한다.
5. **안정적 식별자**: 아이템 Instance는 `FGuid`로 저장과 ViewModel 매핑을 지원한다.
6. **이벤트 기반 UI**: 인벤토리 화면은 상시 Tick에 의존하지 않는다.

상세 구조와 결정 근거는 `INVENTORY_DESIGN.md`를 참조한다.

## 8. 검증 계획

### Model 테스트

- 배치: 경계, 겹침, 회전, 1x1 아이템, 전체 점유
- 이동: 동일/서로 다른 컨테이너, 실패 시 원자성
- 스택: 완전 병합, 부분 병합, 최대치, 서로 다른 상태
- 정렬: 결정론, 실패 시 원상 보존
- 저장: 저장-로드 뒤 InstanceId, 위치, 회전, 수량 동일성
- 리사이즈: 가방 교체로 인한 축소 거부와 확대

### UI 및 성능 목표

- 20x20 스태시, 아이템 100개 시나리오를 프로파일링한다.
- 인벤토리 UI의 상시 Tick 위젯 수는 0을 목표로 한다.
- 셀 수가 아닌 실제 아이템 수 중심으로 위젯 수가 증가하는 렌더 전략을 검토한다.
- 실패한 조작은 사용자에게 설명 가능한 사유를 반환한다.

> 🖼️ **REF-05 · 레퍼런스 이미지** — 대형 스태시 그리드 (정지컷)
**담을 내용**: 셀이 수백 개 규모인 스태시 창고 화면. 아이템이 빽빽하게 찬 상태가 이상적.
**여기 넣는 이유**: 위 성능 목표의 *20x20 셀 = 400셀* 수치가 실제로 어떤 화면인지 보여준다. 셀마다 위젯을 만들면 왜 안 되는지(D1 렌더 전략)를 한 장으로 납득시키는 근거.

## 10. M0에서 확정할 항목

구현 전에 아래 결정이 `Proposed`에서 `Accepted`로 바뀌어야 한다.

1. 아이템 Instance 표현과 컨테이너 소유 구조
2. 그리드 점유 자료구조와 좌표/회전 규약
3. 컨테이너 횡단 연산의 진입점과 실패 결과 타입
4. ViewModel 분할, 변경 통지, 생성/수명 관리
5. 셀 렌더링과 드래그 앤 드롭 구현 경로
6. 저장 레코드와 장비 슬롯 모델

각 결정의 대안과 근거는 인벤토리 설계 문서의 ADR에 남긴다.

## 11. 이미지·영상 자산 규약

두 문서(GDD, 인벤토리 설계)의 모든 시각 자료는 아래 규약을 공유한다.

### 11.1 레퍼런스와 내 구현의 구분 (가장 중요)

포트폴리오에서 레퍼런스 게임 화면과 내 결과물이 섞이면 신뢰를 잃는다. 다음을 **예외 없이** 적용한다.

| 구분 | 접두어 | 캡션 형식 | 위치 |
| --- | --- | --- | --- |
| 레퍼런스 (Escape From Duckov) | `REF-` | `[레퍼런스] Escape From Duckov — 설명` | `ref/` |
| 내 구현 결과물 | `OWN-` | `[내 구현] 설명` | `own/` |
- 캡션의 `[레퍼런스]` / `[내 구현]` 표기는 이미지 바로 아래에 **텍스트로** 넣는다. 이미지에 워터마크로 굽지 않는다(Notion에서 캡션이 검색·복사 가능해야 한다).
- 레퍼런스 이미지에 내 UI 목업을 합성하지 않는다. 비교는 **나란히 배치**로만 한다(OWN-01).

### 11.2 출처 표기

문서 첫 등장 위치(§1 REF-01 아래)와 문서 말미에 한 번씩 표기한다.

> 본 문서의 `REF-` 이미지는 **Escape From Duckov** (개발: Team Soda)의 인게임 화면이며, 설계 레퍼런스 분석 목적으로만 인용했습니다. 해당 저작권은 개발사에 있습니다. 본 프로젝트의 구현물이 아닙니다.
> 
- 인용 목적에 필요한 최소 수량만 사용한다(현재 6장 + GIF 2개 수준을 상한으로 본다).
- 레퍼런스 이미지를 문서의 대표 이미지(Notion 커버, 썸네일)로 쓰지 않는다 — 대표 이미지는 반드시 `OWN-`.
- 게임 로고·타이틀 아트·마케팅 키아트는 사용하지 않는다. 인게임 화면만 사용한다.

### 11.3 캡처 스펙

- 해상도 1920x1080 캡처 후 문서 삽입 시 가로 1200px 내외로 축소. UI 텍스트가 읽히는 것이 기준.
- 관심 영역만 크롭한다. 전체 화면 통짜 캡처는 REF-01, REF-05만.
- GIF: 2~4초, 무음, 12~15fps, 8MB 이하. 조작 한 동작만 담고 앞뒤 여백을 자른다.
- 개인 식별 정보(스팀 계정명, 친구 목록, 오버레이 알림)가 찍히면 크롭하거나 블러 처리한다.
