# ADR-003: Container 소유 구조와 점유 캐시 정책

| 항목 | 내용 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-18 |
| 마일스톤 | M1a 전 |
| 관련 | `INVENTORY_DESIGN.md` A3·A4를 대체 |

## Context / Decision Question — AI

두 갈래 질문을 함께 다룬다.

1. **점유 캐시**: 어떤 칸이 비었는지 찼는지를 그때그때 계산할 것인가, 별도 구조로 유지해서
   바로 조회할 것인가.
2. **Container 소유 구조**: 스태시(월드에 없는 창고)와 레이드 인벤토리(플레이어가 들고 다니는
   것)가 같은 종류의 Container인가, 다른 존재인가. Container가 `AActor`에 묶여야만 존재할 수
   있는가.

## Options — 사용자 먼저(Option Sweep) → AI 보완

사용자가 먼저 낸 답: (1) 그리드처럼 유지해서 바로 조회. (2) 스태시와 레이드 인벤토리는 다른
존재로 본다.

`INVENTORY_DESIGN.md`의 후보: A3 "아이템 목록을 진실로 두고 셀 맵은 재생성 가능한 캐시"(사용자
답과 방향은 같으나 "목록이 진실, 그리드는 캐시"인지 "그리드가 진실"인지는 재확인 필요했음),
A4 "Container는 `UObject`, Component는 Actor 어댑터"(스태시도 레이드와 같은 방식으로 처리하자는
의도였으나 사용자는 "다른 존재"를 택함).

## User Initial Decision — 사용자

1. "그리드처럼 유지해서 바로 조회하는 그림이 맞다고 생각해"
2. "다른 존재로 보는게 맞는거같아. 그리고 container는 actor가 있어야 한다고 생각해"

AI가 "아이템 목록이 진실이고 그리드는 동기화되는 캐시냐, 그리드 자체가 진실이냐"를 재확인하자
(a) 목록이 진실, 그리드는 캐시로 확정. Actor 필요 여부는 AI Review 이후 아래처럼 정정됨.

## User Reasoning / Concerns — 사용자

캐시-목록 동기화가 어긋날 수 있다는 리스크는 인지하고 있고, 구현을 진행하면서 그때그때
자문을 구하기로 함(사전에 전부 설계하지 않음).

## AI Review — AI

최종 판단에 실제로 영향을 준 지적만 남긴다.

- **캐시 동기화는 CLAUDE.md §4의 원자적 커밋 원칙 안에 들어가야 한다.** 추가/삭제/이동/회전마다
  목록과 캐시를 함께 갱신해야 하고, 어긋나면 조용히 깨진다. 사용자가 리스크를 인지하고 구현 중
  자문으로 처리하기로 했으므로 이 결정 자체를 막지는 않음.
- **`AActor` 레벨 전환 생존 문제.** `GDD.md`가 "영속성 — 스태시와 인벤토리 상태 저장/로드",
  "탈출 성공: 레이드에서 획득한 아이템을 스태시에 커밋한다"를 요구하는데, `AActor`는 레벨 전환 시
  기본적으로 사라진다. "Container는 Actor가 있어야 한다"를 스태시에 그대로 적용하면 그 Actor를
  레벨 전환 내내 살려야 하는 문제가 생긴다.
  → 사용자가 **"필요할 때만 Actor에 잠깐 붙여서 보여주는 그림"**으로 정정해 이 문제를 해소했다.
  Container 데이터 자체는 Actor 수명과 무관하게 존재하고, Actor는 표시·상호작용 시점에만 임시로
  붙는다.
- 결정을 뒤집을 만한 반론은 남지 않았다.

## Final Decision — 사용자

1. **점유 캐시**: 아이템 목록이 진실이다. 셀 점유 상태(그리드)는 목록과 동기화되는 캐시이며,
   필요하면 목록에서 재생성할 수 있다. 캐시 갱신은 연산의 원자적 커밋과 같은 트랜잭션에서
   이뤄진다.
2. **Container 소유 구조**: 스태시와 레이드 인벤토리는 **서로 다른 Container 타입**으로 다룬다.
   Container 데이터 자체는 `AActor` 존재와 무관하게 산다. `AActor`는 **상호작용·표시가 필요할
   때만 일시적으로 붙는다.**

## Consequences / Accepted Costs — 사용자

**얻는 것**
- 점유 조회가 매번 계산하지 않고 캐시로 빠르다.
- Container 데이터가 Actor 수명에 묶이지 않아 레벨 전환·저장/로드에 안전하다.
- 두 Container 타입이 서로 다른 존재라 각자 필요한 만큼만 구현하면 된다.

**감수하는 비용**
- 캐시-목록 동기화를 모든 연산에서 정확히 유지해야 한다. 어긋나면 조용히 깨진다 — 구현 중
  자문으로 대응하기로 함.
- 두 Container 타입이 공유 로직을 자동으로 얻지 못한다. 공통 계약(인터페이스)이 필요하면
  Operation Service 설계(`ADR-004`)에서 별도로 다룬다.

## Revisit Conditions — 사용자

아래 중 하나가 관찰되면 이 결정을 다시 연다.

1. 캐시-목록 불일치 버그가 구현 중 반복적으로 발생할 때 — 캐시 유지 전략 자체를 재검토.
2. Actor 부착/해제 방식이 M2의 UMG/MVVM 바인딩과 실제로 마찰을 일으킬 때.

## 검증 — AI

1. Container가 `AActor` 없이 생성·조작·검증 가능함을 Automation Test로 확인한다(Automation Test
   환경 자체가 Actor 없는 순수 Model 검증이므로 이 결정의 전제 조건이기도 하다).
2. 임의의 연산 시퀀스 뒤 "캐시를 목록에서 재생성한 결과"와 "현재 캐시 상태"가 항상 동일함을
   검증하는 테스트를 둔다.
3. GDD의 성능 시나리오(20x20 셀, 아이템 100개)에서 점유 조회가 캐시를 통해 이뤄짐을 확인한다.
