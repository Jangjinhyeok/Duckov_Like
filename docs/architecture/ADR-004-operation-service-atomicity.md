# ADR-004: Operation Service — 정적 함수 조정자

| 항목 | 내용 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-18 |
| 마일스톤 | M1a 전 |
| 관련 | `INVENTORY_DESIGN.md` B1을 대체 · B2(원자성)는 CLAUDE.md §4가 이미 규칙으로 정함 · `ADR-003`(Container 소유 구조) 전제 |

> **범위 주의.** "실패한 연산은 상태를 바꾸지 않는다 / bool이 아니라 실패 사유를 반환한다 /
> 롤백 경로를 만들지 않는다"는 이미 CLAUDE.md §4의 규칙이라 이 ADR에서 새로 결정하지 않는다.
> 이 ADR은 **그 계약을 실행하는 구조**(조정자가 있는가, 어떤 형태인가)만 다룬다. 실패 사유
> enum의 구체적 값이나 함수 시그니처는 §5.3·5.4에 따라 헤더 작성 시 정한다.

## Context / Decision Question — AI

같은 컨테이너 내 이동과 다른 컨테이너 간 이동(스태시 ↔ 레이드)을 처리하는 로직을 어디에
둘 것인가 — Container 클래스 자신이 상대 Container를 받아 처리하는가, 아니면 두 Container를
동시에 다루는 별도 조정자를 두는가.

## Options — 사용자 먼저(Option Sweep) → AI 보완

사용자가 먼저 낸 두 안: (1) Container가 상대 Container를 인자로 받아 처리, (2) 두 Container를
다루는 조정자.

`INVENTORY_DESIGN.md`의 B1 후보: "Operation Service / Request-Result 계층 — 횡단 연산과 실패
이유를 한 곳에서 관리."

## User Initial Decision — 사용자

> "첫 생각은 상대 컨테이너가 받아서 처리하는 그림이었는데, 두 container를 다루는 조정자가
> 더 좋아보인다"

## User Reasoning / Concerns — 사용자

Container끼리 서로를 알고 처리하는 것보다, 별도 조정자가 둘을 동시에 다루는 편이 더 낫다고
재고 후 판단함.

## AI Review — AI

최종 판단에 영향을 준 지적만 남긴다.

- **`ADR-003`이 스태시·레이드를 다른 타입으로 정했으므로**, 조정자가 둘을 동일하게 다루려면
  각 Container가 같은 모양의 최소 계약(조회·검증·적용 메서드)만 맞추면 된다 — 클래스가 같을
  필요는 없다. 헤더 설계 단계에서 자연히 풀리는 문제.
- **원자성 요구 때문에** 조정자는 "검증 → (둘 다 통과하면) 적용"을 분리해서 가져야 한다.
  한쪽만 확인하고 바로 적용하면 다른 쪽이 실패했을 때 롤백 경로가 필요해지는데, CLAUDE.md §4가
  롤백 경로를 만들지 말라고 이미 정했다.
- 결정을 뒤집을 만한 반론은 없었다.

## Final Decision — 사용자

Operation Service는 **상태 없는 정적 함수 모음**으로 둔다. Container(들)를 인자로 받아, 관련된
모든 Container에 대해 먼저 전체 검증을 마친 뒤 한 번에 커밋한다. 동일 컨테이너 내 이동과
다른 컨테이너 간 이동이 같은 경로를 탄다.

## Consequences / Accepted Costs — 사용자

**얻는 것**
- 오브젝트 그래프 없이 정적 함수를 직접 호출해 테스트하기 쉽다.
- `ADR-009`의 전역 카운터(정적 함수)와 스타일이 일관된다.
- 조정자가 상태를 갖지 않으므로 소유권·수명 문제가 없다.

**감수하는 비용**
- 서로 다른 Container 타입(`ADR-003`)이 각각 조정자가 기대하는 최소 계약(조회·검증·적용
  메서드)을 구현해야 한다 — 공통 베이스 클래스 없이 계약만 맞추는 유지보수 부담.

## Revisit Conditions — 사용자

아래 중 하나가 관찰되면 이 결정을 다시 연다.

1. Container 타입이 늘어나 조정자 로직이 타입별 분기로 지저분해질 때 — 공통 인터페이스/베이스
   클래스 도입을 재검토한다.
2. 조정자가 상태(트랜잭션 로그, 캐시 등)를 가져야 할 필요가 실제로 생길 때 — 정적 함수에서
   객체로 전환을 재검토한다.

## 검증 — AI

1. 동일 컨테이너 내 이동과 다른 컨테이너 간 이동이 같은 정적 함수 경로를 탐을 Automation
   Test로 확인한다.
2. 실패 원자성 테스트 — 실패하는 이동 시도 뒤 양쪽 Container 상태가 시도 전과 동일함을
   확인한다(GDD v1 완료 기준과 동일한 조건).
3. Container 인스턴스 없이(또는 최소한의 인스턴스만으로) 정적 함수를 직접 호출할 수 있음을
   확인한다.
