# ADR-002: Item Instance 표현과 `FGuid` 정책

| 항목 | 내용 |
| --- | --- |
| 상태 | Superseded |
| 날짜 | 2026-08-05 |
| 마일스톤 | M1a 전 |
| 관련 | [ADR-009](ADR-009-item-instance-identifier.md)가 대체 · [ADR-000](ADR-000-module-boundaries.md) · INVENTORY_DESIGN의 A2·A3 |

> **폐기 사유 (2026-08-09).** 이 문서의 결정과 근거는 **AI가 제시하고 사용자가 읽고 납득한 것**이며,
> 사용자가 먼저 선택지를 훑고 스스로 내린 판단이 아니다. 설명 역전으로 측정한 결과 사용자가 재생할 수
> 있었던 것은 결론 명사 두 개(`struct`, `FGuid`)뿐이었고 근거·정책·대가는 전부 백지였다.
> 그래서 `Accepted`를 취소하고 결정을 다시 열었다.
>
> **식별자 부분은 [ADR-009](ADR-009-item-instance-identifier.md)가 대체한다** — 재결정 결과는
> `FGuid`가 아니라 전역 카운터가 발급하는 `int32` 번호다.
>
> **나머지 부분은 대체되지 않고 미결로 돌아간다.** `USTRUCT` vs `UObject` 표현 방식과 스택 분할 시
> ID 정책은 사용자 판단을 거친 적이 없으므로 승계하지 않는다. 아래 본문은 **재결정의 대조군으로
> 보존**하며, 구현의 근거로 삼지 않는다.

## 맥락

그리드 인벤토리에서 **아이템 하나를 어떻게 표현하고, 어떻게 가리킬 것인가**를 정해야 한다.
이 결정은 뒤따르는 거의 모든 것을 좌우한다 — Container의 저장 구조(ADR-003),
이동 원자성 구현(ADR-004), 저장 레코드 형식(ADR-007), ViewModel 매핑(ADR-005)이
전부 여기에 기댄다.

식별자가 살아남아야 하는 순간이 넷이다:

1. **정렬** — 면적 내림차순 greedy(B3)가 배열 순서를 뒤섞는다
2. **컨테이너 간 이동** — Source에서 빠지고 Target에 들어간다
3. **저장/로드** — v1 완료 기준에 *"저장-로드 뒤 `InstanceId`가 유지된다"*가 있다
4. **ViewModel 매핑** — Item VM이 "내가 보고 있는 아이템"을 붙잡아야 한다

## 결정

### 1. Instance는 `USTRUCT`

```cpp
USTRUCT(BlueprintType)
struct INVENTORYCORE_API FItemInstance
{
    GENERATED_BODY()

    UPROPERTY(VisibleAnywhere) FGuid   InstanceId;
    UPROPERTY(EditAnywhere)    FName   DefinitionId;
    UPROPERTY(EditAnywhere)    int32   Count = 1;
    UPROPERTY(EditAnywhere)    bool    bRotated = false;
    UPROPERTY(VisibleAnywhere) FIntPoint Position = FIntPoint::ZeroValue;
};
```

Container는 `UObject`로 두고(A4), 아이템은 그 안에 `TArray<FItemInstance>` **값**으로 담는다.

### 2. 식별자는 `FGuid`

전역 고유. 컨테이너를 옮겨 다녀도, 배열이 재정렬돼도, 저장-로드를 거쳐도 불변이다.

### 3. 발급은 팩토리가 전담한다

```cpp
static FItemInstance Create(FName DefinitionId, int32 Count);   // 내부에서 FGuid::NewGuid()
```

**`FItemInstance`는 태어날 때부터 유효한 `InstanceId`를 갖는다.**
"ID가 아직 없는 인스턴스"라는 상태를 표현 불가능하게 만든다.

### 4. 스택 분할 시 원본이 ID를 유지한다

10개를 6+4로 나누면 **원래 자리에 남는 쪽이 기존 `InstanceId`를 지키고, 새로 배치되는 쪽이
`NewGuid()`를 받는다.**

병합은 반대로 ID를 만들지 않는다 — 부분 병합이면 양쪽 모두 기존 ID를 유지한 채 수량만
옮기고, 완전 병합이면 Source가 `Count == 0`이 되어 제거되면서 그 ID가 사라진다.

## 근거

### 왜 `FGuid`인가

가리키는 방법의 후보를 떨어뜨려 보면 남는 것이 이것뿐이다.

| 방법 | 깨지는 지점 |
| --- | --- |
| 포인터 | `TArray` 재할당 시 무효. 저장-로드 후 의미 없음 |
| 배열 인덱스 | 제거·정렬(B3)이 일어나면 전부 어긋남 |
| 이름/문자열 | 동일 아이템 다수일 때 충돌. 비교 비용도 큼 |
| **`FGuid`** | 위 넷을 전부 통과 |

`FGuid`는 UE 내장 `USTRUCT`(`uint32` 4개 = 16바이트)이고 `GetTypeHash`가 정의돼 있어
`TMap` 키로 바로 쓰인다. 직렬화도 자명해 저장 레코드에 그대로 들어간다.

### 왜 `USTRUCT`인가 — A2의 근거는 UObject를 정당화하지 못한다

설계 문서 A2는 `UObject` + `FGuid`를 권하며 근거로 *"UI 매핑, 가변 상태, 저장 식별자에
적합"*을 들었다. 검토 결과 셋 다 UObject여야 할 이유가 아니다:

| A2의 근거 | 실제로 그 일을 하는 것 |
| --- | --- |
| UI 매핑 | `FGuid` — UObject와 무관 |
| 가변 상태 | struct도 가변이다 |
| 저장 식별자 | `FGuid` — 오히려 struct가 저장하기 쉽다 |

**식별을 `FGuid`로 해결하고 나면 UObject를 쓸 이유가 대부분 사라진다.**
남는 실질적 이득은 GC 수명 관리, 리플렉션 기반 디테일 패널 디버깅, 델리게이트 바인딩,
타입별 서브클래싱인데 — v1 범위의 Instance는 **행동이 없는 순수 데이터**라 어느 것도
필요하지 않다.

반대로 `USTRUCT`가 이 프로젝트에서 갖는 이점은 명제와 직결된다:

- **테스트가 단순하다.** 스택에 만들면 끝이다. `NewObject`도 Outer도 GC도 월드 컨텍스트도
  필요 없다. 별도 `InventoryCoreTests` 모듈에서 30개 이상을 돌릴 계획인데, 준비 코드가
  지저분하면 테스트를 덜 쓰게 된다.
- **값 의미론이 원자성과 맞는다.** B2가 요구하는 "사전 전체 검증 후 원자적 커밋"은
  배열을 복사해 검증하고 성공할 때만 교체하는 방식으로 구현된다 — 롤백 경로가 불필요하다.
- **연속 메모리.** 점유 캐시 재생성과 정렬처럼 전체를 순회하는 연산에서 유리하다.
- **MVVM에 UObject Model이 필요 없다.** 바인딩 소스가 되어야 하는 것은
  ViewModel(`UMVVMViewModelBase`)이지 Model이 아니다. INV-08이 요구하는 "VM은 원본 상태를
  소유하지 않는다"는 VM이 Model을 *투영*하라는 뜻이므로, Model이 struct여도 무방하다.

### 왜 팩토리 전담인가

`FItemInstance`를 아무 데서나 기본 생성할 수 있게 두면 `InstanceId`가 비어 있는 구조체가
돌아다니게 된다. 그러면 "유효하지 않은 상태"를 검사하는 코드와 그 상태를 다루는 테스트가
모든 경로에 늘어난다. 팩토리가 항상 발급하면 **그 상태가 애초에 표현 불가능해진다.**

### 왜 원본이 ID를 유지하는가

설계 문서의 드래그 규약과 맞물린다 — *"드래그 시작 시에는 Model에서 아이템을 제거하지
않는다. Drop 성공 때만 실제 이동을 커밋한다."* 즉 **새 인스턴스는 Drop 시점에 생긴다.**
원본은 드래그 내내 제자리에서 살아 있었으므로 ID를 유지하는 것이 자연스럽고,
드롭이 실패하면 아무 ID도 발급되지 않는다.

반대 정책(이동한 쪽이 유지)을 택하면 드롭 실패 시 원래 자리 아이템의 ID가 바뀔 수 있어,
그 셀을 보던 Item VM의 바인딩을 재생성해야 한다.

## 기각한 대안

**`UObject` 기반 Instance (A2 원안).**
중첩 컨테이너(INV-07)를 v1에서 제대로 다룬다면 참조 그래프가 필요해 UObject가 유리하다.
그러나 v1 정책은 *"인터페이스와 순환 검사 계약만 준비, 기능은 P1"*이다. 지금 UObject를
택하면 v1에 쓰지 않을 기능의 비용(테스트 준비 코드, GC, 할당 오버헤드)을 선불로 낸다.
**중첩 컨테이너를 실제로 구현하는 시점에 이 ADR을 superseding하는 것이 옳다.**

**`int32` 단조 증가 카운터.**
싱글플레이고 네트워크가 명시적으로 제외됐으므로 충분히 동작한다. 16바이트 대신 4바이트로
더 가볍고 비교·해시도 싸다. 기각한 이유는 **카운터 자체를 관리해야 하기 때문**이다 —
"다음 번호"의 소유자를 정하고, 저장 파일에 함께 넣고, 로드 시 복원해야 한다.
스태시 세이브와 레이드 세이브를 나중에 분리하면 번호가 겹친다.
`FGuid`는 그 관리 부담을 12바이트로 산 것이며, 아이템 100개 규모에서 차이는 약 1.2KB로
무의미하다.

**포인터 · 배열 인덱스 직접 참조.** 위 표대로 정렬·저장에서 깨진다.

**Container가 추가 시점에 ID 발급.**
"어느 컨테이너에도 속하지 않은 아이템"을 구분할 수 있다는 이점이 있으나,
ID가 빈 구조체가 존재할 수 있게 되어 버그 면적이 늘어난다.

## 결과

**얻는 것**

- Model 계층이 UObject 의존 없이 성립한다. ADR-000의 모듈 경계와 정합적이다.
- 테스트 준비 코드가 한 줄이다 — `FItemInstance::Create(TEXT("Ammo"), 30)`.
- 저장 레코드 매핑이 거의 항등에 가깝다(ADR-007에서 활용).
- 원자적 커밋을 복사-검증-교체로 구현할 수 있어 롤백 경로가 불필요하다.

**감수하는 비용**

- **`FGuid` → 인덱스 조회 캐시가 필요하다.** `TMap<FGuid, int32>`를 유지하거나 선형 탐색을
  해야 한다. A3의 점유 캐시와 같은 성격의 관리 부담이 하나 더 붙는다(ADR-003에서 확정).
- **값 복사가 INV-01을 조용히 깰 수 있다.** `FItemInstance`를 복사하면 같은 `InstanceId`가
  둘이 된다. UObject였다면 포인터 공유라 이 사고가 없다.
  → **완화**: 아이템의 생성·이동·제거는 Operation Service만 수행하고,
  이동은 반드시 "Source 제거 + Target 추가"를 한 트랜잭션으로 커밋한다.
  중복 ID 부재를 검증하는 테스트를 둔다.
- **중첩 컨테이너를 도입할 때 전환 비용이 있다.** 지금 내지 않는 대신 나중에 낼 수도 있는
  비용이다.

## 검증

Model Automation Test로 검증한다. 실제 테스트 이름은 M1a 시작 시 사용자가 확정한다
(CLAUDE.md 5.2). 이 ADR이 요구하는 검증 지점은 다음과 같다.

1. **발급 불변식** — 팩토리로 만든 인스턴스는 항상 `InstanceId.IsValid()`가 참이다.
2. **고유성** — 같은 Definition으로 여러 번 생성해도 `InstanceId`가 서로 다르다.
3. **분할 정책** — 스택을 나누면 원본의 `InstanceId`가 보존되고 새 쪽만 다른 ID를 받는다.
4. **병합 정책** — 부분 병합은 양쪽 ID를 모두 보존하고, 완전 병합은 Source를 제거한다.
5. **컨테이너 간 이동 후 ID 보존** — 이동에 성공해도 `InstanceId`는 바뀌지 않는다.
6. **중복 ID 부재** — 임의의 연산 시퀀스 후 한 컨테이너 안에 같은 `InstanceId`가 둘 이상
   존재하지 않는다 (INV-01, 위 "값 복사" 비용에 대한 방어선).
7. **저장 라운드트립** — 저장-로드 후 `InstanceId`·위치·회전·수량이 동일하다
   (v1 완료 기준, ADR-007에서 함께 검증).
