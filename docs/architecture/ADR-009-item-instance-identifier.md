# ADR-009: 아이템 Instance 식별자 — 전역 카운터가 발급하는 `int32`

| 항목 | 내용 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-08-09 |
| 마일스톤 | M1a 전 |
| 관련 | [ADR-002](ADR-002-item-instance-and-guid.md)를 대체(식별자 부분) · GDD 아키텍처 원칙 5번 |

> **범위 주의.** 이 ADR은 **식별자만** 다룬다. ADR-002가 함께 담고 있던 *Instance를 `USTRUCT`로 둘
> 것인가 `UObject`로 둘 것인가*와 *스택 분할 시 ID 정책*은 이 결정에 포함되지 않으며 **미결로
> 남는다.** ADR-002가 그 둘에 대해 내린 결론은 사용자 판단이 아니었으므로 승계하지 않는다.

## Context / Decision Question — AI

인벤토리에 같은 종류의 아이템이 여러 개 존재한다(9mm 탄약 두 뭉치). 코드가 그중 **특정
하나**를 지목해 계속 붙잡고 있어야 하는데, 그 수단을 무엇으로 할 것인가.

아이템은 개체마다 다른 상태를 갖는다(GDD: *"Definition 참조, 수량, 회전, 위치, 내구도 등 가변
상태를 Instance로 관리"*). 따라서 "같은 종류"와 "같은 물건"은 구별되어야 한다.

## Options — 사용자 먼저(Option Sweep) → AI 보완

사용자가 도메인 추론으로 먼저 낸 후보는 **격자 좌표 `(x, y)`** 였다. AI가 보탠 후보는 배열
인덱스, 메모리 주소, 이름 문자열, 순차 번호표(`int32`), `FGuid`다.

사용자가 여섯 가지 상황을 예측하며 후보를 걸러냈고, 그 과정에서 **지목 수단이 만족해야 할
조건을 직접 도출했다.**

| | 조건 (사용자 도출) |
| --- | --- |
| 1 | 이름표는 물건에 붙어 있다 — 자리·순서·가방이 바뀌어도 물건을 따라간다 |
| 2 | 같은 종류여도 개체마다 다르다 |
| 3 | 껐다 켜도 살아남는다 |

사용자가 (d)(e) 상황에서 쓴 문장이 조건 1의 원문이다:

> "0,2 탄약에 이름 붙인거고 그걸 옮긴거니까 0,2는 이름표가 없지"

즉 **이름표는 칸이 아니라 물건에 붙어 있고, 물건이 움직이면 같이 간다.**

| 후보 | 판정 |
| --- | --- |
| 배열 인덱스 | 탈락 — 제거·정렬이 순서를 흔든다. 제거 구현 방식에 따라 조용히·조건부로 깨진다 |
| 격자 좌표 | 탈락 — 조건 1 위반. 좌표는 "어디"를 가리키지 "무엇"을 가리키지 않는다 |
| 메모리 주소 | 탈락 — 조건 3 위반 |
| 이름 문자열 | 열등 — 번호표와 관리 부담이 같고 비교가 느리다 |
| **순차 번호표 `int32`** | 통과 |
| `FGuid` | 통과 |

## User Initial Decision — 사용자

> "fguid가 거시적인 측면에서는 물론 좋은건 백번 이해하겠는데, 이건 토이프로젝트이고 내가
> 보여주고싶은건 ui를 어떻게 만들고 다루었는지 잖아? 거기에 fguid를 썼다는 그냥 한 줄 정도로
> 넘어가는 거인 것에 반해서 앞으로의 코딩에서 fguid를 사용하는거보단 int가 더 내 방향성에
> 맞을거같아."

## User Reasoning / Concerns — 사용자

- 이 프로젝트가 증명하려는 축은 UI다. GDD의 한 줄 요약도 *"UI 프로그래밍 포트폴리오 프로젝트"* 다.
- 식별자 선택은 포트폴리오에서 한 줄로 지나가는 항목이다. 거기에 무게를 두지 않는다.
- 앞으로 계속 코드를 만지는 동안 `int`가 더 다루기 편한 방향이다.

## AI Review — AI

최종 판단에 실제로 영향을 준 지적만 남긴다.

- **근거 교정.** "쓰기 편해서"는 부정확하다. `FGuid`도 생성 한 줄, 맵 키로 그대로 사용, 저장
  자동이라 작성 난이도는 거의 같다. 실제 차이는 **로그·디버깅 가독성**이다 —
  `아이템 37번` vs `아이템 a3f9c1d2-…`. 인벤토리는 눈으로 상태를 좇는 디버깅이 잦아 이 차이가 작지 않다.
  → 사용자가 받아들여 근거를 "읽기 편해서"로 확정.
- **발급 충돌 위험.** GDD에 스태시 저장과 인벤토리 저장이 분리돼 있다. 카운터를 각각 두면
  레이드에서 발급한 3번과 스태시의 3번이 탈출 정산(M3) 시점에 충돌해 아이템이 조용히 사라진다.
  → 사용자가 **카운터를 전역 단 하나**로 두기로 결정. 위험이 설계 요구사항으로 전환됐다.
- **새 결정이 하나 늘어난다.** `FGuid`와 달리 "다음 번호"를 기억하는 주체가 필요하다.
  전역 단일화로 소유자는 정해졌으나 **저장/로드 시 카운터 복원 규칙은 미결**이다.
- **테스트 영향은 양날.** 초기화하지 않으면 실행 순서에 따라 ID가 달라져 테스트가 흔들린다.
  반대로 초기화 규칙만 세우면 ID가 `1, 2, 3`으로 예측 가능해져 `FGuid`보다 검증하기 쉽다.

## Final Decision — 사용자

> "근거는 읽기 편해서로 바꾸고, 카운터는 전역 하나로 가자"

1. 아이템 Instance의 식별자는 **`int32` 순차 번호**로 한다.
2. 채택 근거는 **로그·디버깅에서 사람이 읽을 수 있다는 것**이다.
3. 번호를 발급하는 **카운터는 스태시·레이드가 공유하는 전역 단 하나**로 둔다.

## Consequences / Accepted Costs — 사용자

**얻는 것**
- 로그와 디버깅에서 식별자를 사람이 그대로 읽는다.
- 식별자 4바이트. `FGuid` 대비 개당 12바이트 절감(수백 개 규모에서 실익은 미미).
- 테스트에서 ID가 예측 가능해 검증문을 직접 쓸 수 있다.

**감수하는 비용**
- **카운터를 관리해야 한다.** 저장 파일에 다음 번호를 함께 넣고 로드 시 복원해야 한다.
  `FGuid`에는 없던 일이다.
- **전역 단일 카운터가 강제된다.** 저장소를 나중에 분리하고 싶어져도 이 제약이 남는다.
- **테스트 초기화 규칙이 필요하다.** 없으면 실행 순서에 따라 테스트가 흔들린다.

## Revisit Conditions — 사용자

아래 둘 중 하나가 관찰되면 이 결정을 다시 연다.

1. **네트워크/멀티플레이가 도입되면.** 현재 범위에서 명시적으로 제외돼 있고 계획도 한참 뒤지만,
   도입 의사 자체는 있다. 여러 클라이언트가 각자 번호를 발급하는 순간 전역 단일 카운터 전제가
   깨진다.
2. **"읽기 편해서"라는 채택 근거가 실제로 성립하지 않으면.** 이 결정의 유일한 근거이므로 근거가
   무너지면 결정도 무너진다. 다음 중 하나가 관찰되는 경우다.
   - M1a~M2를 구현하는 동안 번호를 로그로 좇아 디버깅하는 일이 실제로는 거의 없었다 → 이점이 없다
   - 반대로 카운터 관리 비용(저장 시 다음 번호 보관, 로드 시 복원, 테스트마다 초기화)이 예상보다
     크게 걸리적거렸다 → 관리가 불필요한 대안이 유리해진다

   다른 조건과 달리 **M1a~M2 안에 답이 나오므로 실제로 점검 가능한 조건**이다.

### 검토했으나 조건에서 제외한 것

| 후보 | 제외 사유 |
| --- | --- |
| 아이템 외부 임포트 · 모드 지원 | 하지 않기로 결정했으므로 조건이 되지 않는다 |
| 세이브 파일이 여러 개가 되거나 세이브끼리 아이템을 주고받게 될 때 | 계획에 없고 판단 근거가 없다. 슬롯이 서로 독립적이면 번호가 겹쳐도 만날 일이 없으므로 문제 자체가 생기지 않는다 |
| 중첩 컨테이너 도입 | **식별자를 흔들지 않는다.** 전역 카운터는 파우치든 탄약이든 번호를 발급하면 그만이고 중첩돼도 번호는 따라간다. 압박이 걸리는 쪽은 표현 방식(`USTRUCT` 값 복사 vs `UObject` 참조)이므로 그 결정의 Revisit Condition으로 이관한다 |

## 검증 — AI

Model Automation Test로 검증한다. 테스트 이름은 M1a 시작 시 사용자가 확정한다.

1. **발급 불변식** — 생성된 인스턴스는 항상 유효한 번호를 갖는다.
2. **고유성** — 같은 Definition으로 여러 번 생성해도 번호가 서로 다르다.
3. **이동 후 보존** — 다른 칸·다른 컨테이너로 옮겨도 번호가 바뀌지 않는다 (조건 1).
4. **제거 무영향** — 다른 아이템이 제거돼도 남은 아이템의 번호가 바뀌지 않는다 (조건 1).
5. **저장 라운드트립** — 저장-로드 후 번호가 동일하다 (조건 3).
6. **카운터 복원** — 로드 직후 발급하는 번호가 기존 번호와 충돌하지 않는다.
7. **전역 단일성** — 스태시와 레이드에서 각각 발급해도 번호가 겹치지 않는다.

## 이 ADR이 열어 둔 것

- **Instance를 `USTRUCT`로 둘 것인가 `UObject`로 둘 것인가** — 미결.
  이 결정의 Revisit Condition에 **중첩 컨테이너 도입**을 포함시킬 것 (위 제외 표 참조)
- **번호를 언제 누가 발급하는가** (생성 시점인가, 컨테이너 편입 시점인가 / "번호 없는 인스턴스"를 허용하는가) — 미결
- **스택 분할 시 어느 쪽이 기존 번호를 유지하는가** — 미결
- **저장/로드 시 카운터 복원 규칙** — 미결
- **테스트 카운터 초기화 규칙** — 미결
