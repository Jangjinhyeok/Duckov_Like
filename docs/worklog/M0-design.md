# M0 — 설계와 ADR 승인

기간: 2026-08-05 ~ · 상태: **진행 중**

## 목표

구현 전에 확정해야 할 구조 결정을 ADR로 남긴다.

이 마일스톤의 실질 과제는 ADR을 몇 개 쓰느냐가 아니라 **그 결정이 실제로 누구의 판단인가**를
성립시키는 것이다. 프로젝트의 명제가 "구조를 직접 설계했다"이므로, 결정의 출처가 문서로
입증되지 않으면 명제 자체가 서지 않는다.

---

## 작업 내역

### 하네스 문서 정정 — 빌드 명령과 ADR glob (미커밋)

`CLAUDE.md`와 `AGENTS.md`의 빌드 명령에 primary tree 절대경로가 박혀 있었다. Codex Builder는
별도 worktree에서 도는데, 이대로면 **자기 변경이 아니라 primary tree를 빌드하고
`Result: Succeeded`를 보고한다.** 검증값이 통째로 거짓 신호가 되는 구조였다.

선택지 셋을 놓고 실측했다.

```
-Project="DuckovLike.uproject"      -> Unable to find project file / Result: Failed (0.18초)
-Project=".\DuckovLike.uproject"    -> Unable to find project file / Result: Failed (0.15초)
-Project="$PWD\DuckovLike.uproject" -> Result: Succeeded (1.73초)
-Project="%CD%\DuckovLike.uproject" -> Result: Succeeded (1.35초)   (cmd)
```

상대 경로가 실패하는 이유는 `Build.bat`이 UBT를 부르기 전에 `pushd`로 CWD를 엔진의
`Engine/Source`로 바꾸기 때문이다. 호출자의 CWD는 UBT에 도달하지 않는다.

셸이 CWD를 전개하는 형태를 채택하고, Builder worktree에서 end-to-end로 확인했다.

```
검증: (Duckov_Like-build worktree에서) Build.bat ... "-Project=$PWD\DuckovLike.uproject"
  -> -Project=C:\...\Duckov_Like-build\DuckovLike.uproject
  -> 12개 액션 실제 컴파일 -> Result: Succeeded (109.05초)
```

`Target is up to date`가 아니라 worktree의 소스를 실제로 컴파일했다는 점이 핵심이다.
거짓 신호 경로가 닫혔다.

`ADR-TEMPLATE.md`가 `docs/architecture/ADR-*.md` glob에 걸리는 문제는 표의 해당 행에 예외를
적어 해결했다. 규칙과 예외를 한 셀에 두어, 표만 읽는 쪽이 예외를 놓치지 않게 했다.

### 설계 주도권 감사

빌드 명령 수정 후, 원래 목적이 "아키텍처 주도권 확보"였는데 그것이 적용됐는지 점검했다.
파일을 열어 확인한 결과:

- `ADR-002`가 `Accepted` 상태인데 `User Initial Decision`·`User Reasoning`·`AI Review`·
  `Revisit Conditions` 절이 하나도 없었다. 어디까지가 사용자 판단인지 구분할 표시가 없었다.
- `docs/GDD.md`의 설계 원칙 5번에 `FGuid`가 이미 박혀 있었다. `ADR-002`는 그것을 상세화한
  문서였다. 즉 결정의 뿌리는 ADR이 아니라 GDD였다.
- 강제 수단이 산문뿐이었다. `builder_guard`는 Claude의 `docs/architecture/*.md` 쓰기를
  허용하므로, AI가 사용자 칸을 대신 채우는 것을 막는 기계 장치가 없다.

확인 결과 `GDD.md`와 `INVENTORY_DESIGN.md`도 AI와 함께 만든 문서였다. 설계 사슬 전체가
AI 발원이었다.

### 설명 역전 측정 — `ADR-002`

문서를 덮고 기억만으로 답하게 했다. 추측 금지, "모르겠다"를 정답으로 인정.

| | 질문 | 답 | 판정 |
| --- | --- | --- | --- |
| 1 | 무엇을 정하는 문서인가 | "인벤토리 내부 데이터 구조" | 부분 — 경계가 넓음. 컨테이너 구조는 ADR-003 |
| 2 | 무엇으로 표현하나 / 대안은 | "struct와 fguid를 **추천받았어**" | 답만 맞음. 버린 대안과 이유는 없음 |
| 3 | 왜 그 식별 방법인가 | 모르겠어 | 없음 |
| 4 | 언제 누가 발급하나 | 모르겠어 | 없음 |
| 5 | 스택 분할 시 ID | 모르겠어 | 없음 |
| 6 | 치르는 비용 | 모르겠어 | 없음 |
| 7 | 재검토 조건 | 미답 | 문서에도 없음 |

**남은 것은 명사 두 개뿐이었고 근거·정책·대가는 전부 백지였다.**

이 측정의 부수 효과가 컸다. 측정 전에는 "이미 다 읽었으니 순수한 Option Sweep은 불가능하다"고
판단했는데, 실제 오염은 훨씬 얕았다 — 3~6번은 기억이 아예 없어 사실상 백지에서 다시 결정할 수
있었다. **재결정이 불가능하다는 가정 자체가 틀렸다.**

### 경로 결정 — 과거는 라벨링, 미래는 절차

과거 산출물을 전부 재결정하는 것은 시간상 불가능하고, 오염 때문에 형식만 밟는 연극이 되기
쉽다. 반대로 그대로 두면 포트폴리오의 핵심 주장이 뿌리에서 비게 된다.

**과거는 출처를 정직하게 라벨링해 닫고, `ADR-009` 이후는 절차를 실제로 밟는다**로 정했다.
식별자 결정만 예외적으로 재결정했다 — M1a의 기반이고, 측정 결과 오염이 얕았기 때문이다.

### `ADR-002` 폐기, `ADR-009` 신규

식별자를 `FGuid`에서 **전역 순차 카운터가 발급하는 `int32` 번호**로 재결정했다.

`ADR-002`는 `Superseded`로 닫되 본문을 지우지 않았다. "AI 제안 → 사용자 재결정"의 **대조군**으로
남기는 편이 이 프로젝트에서 값이 있다.

**대체 범위를 식별자로 한정했다.** `ADR-002`가 함께 담고 있던 `USTRUCT` vs `UObject` 표현 방식과
스택 분할 시 ID 정책은 사용자 판단을 거친 적이 없으므로 승계하지 않고 **미결로 되돌렸다.**
그것까지 끌어왔으면 고치려던 문제를 그대로 반복하는 셈이다.

### 파생 문서 갱신

```
docs/GDD.md              아키텍처 원칙 5번  FGuid -> 전역 순차 카운터 int32
docs/INVENTORY_DESIGN.md A2 상태 칸 / 검증 매트릭스 GUID -> Instance 번호 / 승인 ADR 목록
README.md                설계 원칙 표의 식별자 행 / ADR 상태 문장
```

`INVENTORY_DESIGN.md`의 A2는 제안·이유 칸을 원문 그대로 두고 상태 칸만 갱신했다. 당시 제안이
무엇이었는지가 기록으로 남아야 대조가 되고, A2가 `UObject`와 `FGuid`를 한 덩어리로 묶어 놓은 것
중 우리가 재결정한 것은 뒤쪽뿐이기 때문이다.

## AI 활용

### 내가 결정한 것

`ADR-009`의 원문을 인용한다.

> **User Initial Decision** — "fguid가 거시적인 측면에서는 물론 좋은건 백번 이해하겠는데, 이건
> 토이프로젝트이고 내가 보여주고싶은건 ui를 어떻게 만들고 다루었는지 잖아? 거기에 fguid를
> 썼다는 그냥 한 줄 정도로 넘어가는 거인 것에 반해서 앞으로의 코딩에서 fguid를 사용하는거보단
> int가 더 내 방향성에 맞을거같아."

> **Final Decision** — "근거는 읽기 편해서로 바꾸고, 카운터는 전역 하나로 가자"

그 밖에 내가 문장으로 남긴 결정:

- **과거는 라벨링, 미래는 절차** 경로 선택
- **자동 정렬을 만들지 않는다** — "b 일단 안만들거야"
- **외부 임포트·모드 지원을 하지 않는다** — 따라서 Revisit 조건에서 제외
- **Revisit Conditions 채택**: 네트워크/멀티플레이 도입 시 · 채택 근거가 실제로 성립하지 않을 시
- **지목 수단이 만족해야 할 조건 3가지**를 상황 예측을 통해 직접 도출.
  그중 조건 1의 원문 — "0,2 탄약에 이름 붙인거고 그걸 옮긴거니까 0,2는 이름표가 없지"
- **재결정을 미룬다는 판단** — "inventory design 자체를 내가 전부 이해하지 않고 있고 어떤 내용이
  왜 여기에 들어갔는지 조차 이해하지 못했기에 그걸 이해하고 납득했을 때 해당 결정을 다시 열자"

### AI가 수행한 것

- 주도권 감사, 설명 역전 측정 설계와 채점
- 상황 제시(예측 과제), 후보 보완, 사실 설명(메모리 주소·카운터·`FGuid`의 성질)
- 결정에 대한 반론 — 근거 교정, 발급 충돌 위험 지적, 테스트 영향 분석
- 문서 작성: `ADR-009`, `ADR-002` 폐기 처리, 이 작업 기록
- Codex Builder dispatch와 diff 리뷰, 빌드 실측

### 내가 반려·수정한 것

- **AI가 "배열 인덱스로 지목"을 전제로 깔았음을 지적했다.** 그리드 인벤토리에서 아이템을 빼면
  다른 아이템이 당겨지지 않는다는 점을 짚었고, 이 반론에서 **격자 좌표라는 후보가 나왔다.**
  AI가 목록에 넣지 않았던 것이다.
- **AI가 설계한 spike(직접 코드를 짜서 벽에 부딪히는 방식)를 채택했다가 철회했다.** UE5에서
  전부 직접 작성하는 부담이 목적에 비해 컸다.
- **AI의 표 채우기 과제를 반려했다** — "꼭 필요한 과정이야?". AI가 불필요함을 인정하고 절차를
  걷어냈다. 이후 결정까지 한 번에 도달했다.
- **AI의 Revisit 후보 "중첩 컨테이너"에 예시를 요구했다.** 설명 과정에서 AI가 오분류를 인정하고
  철회했다 — 중첩은 식별자가 아니라 표현 방식에 걸리는 조건이다.
- **AI가 제시한 근거 "쓰기 편해서"를 "읽기 편해서"로 교정한 지적은 수용했다.**

## 막혔던 것

### 상대 경로 `-Project`가 UE 5.7에서 동작하지 않음

`Build.bat`이 `pushd`로 CWD를 엔진 디렉터리로 바꾸므로 호출자의 CWD가 UBT에 도달하지 않는다.
문서 수정 전에 실측해서 확인했다. 셸이 CWD를 전개하는 형태로 우회했다.

### Codex Builder가 두 번 BLOCK — 둘 다 AI의 게이트 명세 결함

| | 원인 |
| --- | --- |
| 1차 | 검증 조건이 "파일당 `Build.bat` 1줄"인데 삽입을 지시한 산문에도 `Build.bat`이 있어 자기모순 |
| 2차 | 저장 행 selector가 prefix 매칭이라 다른 행까지 함께 집계됨 |

두 번 다 작업 자체는 정확히 완료돼 있었고, Builder는 조용히 우회하지 않고 원인을 지목하며
멈췄다. 공통 원인은 **assertion을 실제 파일에 대보지 않고 작성한 것**이다.
처방: dispatch 전에 변경 전 파일로 한 번 돌려 "의도한 이유로 실패하는지" 확인하고,
prefix 매칭 대신 정확한 행 매칭을 쓴다.

### HANDOFF가 커지면 dispatch 자체가 실패한다

이 작업 기록을 HANDOFF 본문에 통째로 담았더니 17KB가 되었고, dispatch가 617ms 만에
`The command line is too long.`으로 죽었다. orchestrator가 HANDOFF 내용을 명령줄 인자로
넘기기 때문에 Windows 명령줄 길이 제한에 걸린다.

우회: 긴 본문을 별도 `HANDOFF*` 파일에 두고 HANDOFF는 그 파일을 참조만 하게 했다.
**문서 lane에서 긴 산출물을 다룰 때 반복될 제약이다.**

### Option Sweep이 백지로 나옴

`ADR-009`를 설계 결정 절차로 재결정하려 했으나 첫 시도에서 답이 나오지 않았다. 원인은 절차가
아니라 **이해 부족**이었고, 사용자가 스스로 진단해 중단을 판단했다. 이후 상황 예측 방식
(AI가 상황 제시 → 사용자가 먼저 예측 → 확인 → 빗나간 자리가 벽)으로 바꾸자 진행됐다.

교훈: **Option Sweep은 문제의 형태를 아는 상태를 전제한다.** 모르는 상태에서 돌리면 형식만
남는다.

### 비유가 오해를 만듦

식별자를 "이름표"라고 부른 것이 **게임 안의 기능**으로 읽혔다. 플레이어에게 보이지 않는 내부
장부라는 점을 명시하고 나서야 논의가 이어졌다.

## 다음으로 넘길 것

### M1a를 막고 있는 것

`ADR-009`가 열어 둔 다섯 가지. 특히 첫 번째가 없으면 헤더의 타입 이름조차 못 쓴다.

- **Instance를 `USTRUCT`로 둘 것인가 `UObject`로 둘 것인가** — 미결
- 번호를 언제 누가 발급하는가 ("번호 없는 인스턴스"를 허용하는가)
- 스택 분할 시 어느 쪽이 기존 번호를 유지하는가
- 저장/로드 시 카운터 복원 규칙
- 테스트 카운터 초기화 규칙

### 판단이 필요한 미결 주제

- **자동 정렬 제거**를 `GDD.md`의 기능 목록과 데모 영상 시나리오에 반영
- 아이템에 플레이어가 이름을 붙이는 기능 + 병합 시 경고 modal (논의 중 나온 아이디어)
- 이미 뭔가 있는 칸에 떨어뜨렸을 때의 배치·스택 규칙
- **`CLAUDE.md` 5.3·5.4 규칙과 실제 작업 스타일의 충돌** — 헤더와 테스트 이름을 구현 전에
  확정하라는 규칙이 "구현하다 떠오르면 추가하는" 방식과 맞지 않는다. 규칙 쪽도 AI가 쓴 것이며
  검증된 적이 없다.

### 발견했으나 처리하지 않은 것

- `INVENTORY_DESIGN.md`의 자동 정렬 항목에 **왜 그 기능이 있어야 하는지에 대한 근거가 없다.**
  언급 7군데가 전부 구현 방법이거나 기능 목록이다. 같은 패턴이 `FGuid`에도 있었다 —
  무엇을 쓰는지는 적혀 있고 왜 그것인지는 없다.
- 이번 세션의 산출물은 **전부 미커밋**이다. Builder worktree는 `HEAD` 기준으로 만들어지므로,
  커밋하지 않으면 다음 dispatch마다 baseline을 수동으로 맞춰야 한다.
